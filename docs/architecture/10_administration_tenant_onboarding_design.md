# Design Specification: Administration & Tenant Self-Service (Phase 6)

## 1. Context & Motivation
Currently, PactaFlow requires manual developer intervention to onboard every new B2B client (tenant). To scale, the product must provide self-service capabilities. Any transport company should be able to self-register, configure its own SLA rules, manage its team, and operate autonomously.

This phase also addresses critical infrastructure gaps in JWT handling and RBAC (Role-Based Access Control) necessary for secure multi-tenancy.

## 2. Organization Management
A "Tenant" in PactaFlow is an `Organization`.
- **Enrichment:** The `organizations` table will be enriched with:
  - `timezone`: For localizing operational events and SLA windows.
  - `currency_code`: For financial projections (default: BRL).
  - `logo_url`: For white-labeling reports and the dashboard.
- **Self-Registration:** A public `/register` route and a `register_new_organization` RPC will allow atomic creation of an organization and the first `TENANT_ADMIN` user.

## 3. RBAC Model (3 Roles)
User roles are refactored from 4 to 3 simplified roles:
1. **Admin (`TENANT_ADMIN`):** Full control over organization settings, users, and SLA rule configurations.
2. **Operator:** Day-to-day operations. Can manage contracts, zones, and declare plans. **Cannot** edit global SLA rule parameters.
3. **Auditor:** Read-only access to dashboards, reports, and exports. Useful for financial investigation and external auditing.

| Permission | Admin | Operator | Auditor |
| :--- | :---: | :---: | :---: |
| `canManageOrganization` | ✅ | ❌ | ❌ |

## 4. JWT & Multi-Tenancy Foundation
Every Row-Level Security (RLS) policy must be unified to a canonical path:
`(auth.jwt() -> 'app_metadata' ->> 'org_id')::uuid`

This depends on the `custom_access_token_hook` being active in Supabase, which injects `org_id` and `role` into every JWT generated by the system.

## 5. User Invitation Flow
1. **Invite:** Admin sends invitation via email.
2. **Persistent Token:** An `invitations` table tracks the invite (email, role, organization, unique token).
3. **Acceptance:** User clicks a link (`/accept-invite?token=...`), creates a password, and the system automatically assigns the pre-defined role and organization to their profile via the hook.

## 6. Rule Configuration Studio
A visual editor for SLA parameters (e.g., `max_dwell_seconds`, `delay_tolerance`).
- **Immutability Invariant:** If a rule set is referenced by an **active** plan, editing it creates a **new version**. Existing historical data remains linked to the old version to preserve the audit trail (Deterministic Replay).

## 7. Contract Approval Workflow
Contracts do not transit automatically to `active`.
1. **Draft:** Created by Operator/Admin.
2. **Awaiting Contractor Acceptance:** Link generated for the contractor (e.g., Caterpillar) to review zones/rules.
3. **Active:** Transits after contractor signs/accepts via a public review page or Admin override.

## 8. Implementation Sequence (9 Blocos)
1. **BLOCO 1:** JWT Infrastructure & Auth Foundation
2. **BLOCO 2:** Contractor Aggregate & Zone FK Migration
3. **BLOCO 3:** RBAC Guards & Permission Layer
4. **BLOCO 4:** Admin Panel & Org Management UI
5. **BLOCO 5:** User Invitation Flow
6. **BLOCO 6:** Contract Approval Workflow

8. **BLOCO 8:** Asset Manager (Vehicles, Drivers, Routes)
