# Design Spec: B2B Contract Management Refactoring

## 1. Problem Definition
The current Contract Creation and Plan Declaration flow suffers from a severe infrastructure leakage into the commercial domain. Operators are forced to manually input raw GPS coordinates (latitude, longitude, radius) and absolute UTC timestamps for every single service execution (SET). 

This approach does not reflect the reality of B2B Corporate Charter (Fretamento Corporativo B2B) in Brazil, where contracts are negotiated based on:
1. **Operational Zones/Named Locations**: "Garagem", "Portaria Sul", "Ponto Matriz", not `(-23.5505, -46.6333)`.
2. **Shift Patterns (Padrões de Turno)**: "Segunda a Sexta, chegada às 07:00", not a manual array of 50 specific dates and times.
3. **SLA Penalties (Ofensores de Margem)**: Clear financial rules for No-Show, Time Delays (Tolerância de Atraso), and Fleet Downgrade (Veículo Inadequado).

## 2. Proposed Architecture & Domain Changes

The domain models `Contract` and `PlanDeclaration` must be refactored to speak the ubiquitous language of the B2B business. The Evaluation Engine will be upgraded to project specific `ContractualServiceExecution` instances dynamically from the `ShiftPattern` schedule.

### 2.1. New Domain Entities (Core)
- **`OperationalZone`**: Represents a named geofenced area. Contracts will reference `zoneId`s instead of hardcoding lat/lng. The normalizer/infrastructure will resolve the `zoneId` to spatial coordinates for the Evaluation Engine.
- **`ShiftPattern`**: Defines the recurrence of a service (e.g., `daysOfWeek: [Mon, Tue, Wed, Thu, Fri]`, `arrivalTimeLocal: "07:00"`, `timezone: "America/Sao_Paulo"`).
- **`SLAPenalties`**: A value object embedded in the contract or shift pattern defining:
  - `noShowPenaltyMultiplier` (e.g., 1.5x)
  - `delayToleranceMinutes` (e.g., 15 mins)
  - `delayPenaltyPerMinute` (e.g., R$ 10.00)
  - `downgradePenaltyFlat` (e.g., R$ 500.00)

### 2.2. Schema Changes (Immutable Ledger & Projections)
We will introduce new tables and modify existing ones, preserving the append-only nature of the ledger.

#### [NEW] `operational_zones` table
Stores the mapping between commercial names and spatial data.
- `id` (UUID, PK)
- `organization_id` (UUID, FK)
- `name` (TEXT)
- `latitude` (DOUBLE PRECISION)
- `longitude` (DOUBLE PRECISION)
- `radius_meters` (INTEGER)

#### [MODIFY] `plan_declarations` table / payload
The JSONB payload (or a new related table `shift_patterns`) will store the abstract shift rules rather than raw `contractual_service_executions`. The Evaluation Engine will run a daily cron/sweep to project the next N days of `contractual_service_executions` based on the active `PlanDeclaration` and its `ShiftPattern`s.

#### [MODIFY] `contractual_service_executions` table
- Remove `contractual_value`, `no_show_penalty_multiplier` from being hardcoded per SET if they can be inherited from the SLAPenalties, OR keep them denormalized but generated by the engine, not the human.
- Add `delay_tolerance_minutes`.
- Add `expected_vehicle_category_id`.

## 3. UI/UX Proposal (Operations Control Room)
The `DeclareContractPlanForm` will be completely redesigned. 

### 3.1. Removal of Lat/Long
The form will feature dropdowns or autocomplete fields querying the `operational_zones` table for Origin and Destination.

### 3.2. Shift and Recurrence Form
Instead of "Start UTC" and "End UTC", the operator will configure:
- **Days of Week**: Checkboxes (S M T W T F S)
- **Arrival Time Limit**: Time picker (Local time).
- **Departure Time**: Time picker (Local time).

### 3.3. SLA Configuration Card
A dedicated section for margin offenders:
- **No-Show**: Penalty multiplier input.
- **Delay**: Tolerance window (minutes) and fine value.
- **Downgrade**: Expected category dropdown and fine value.

## 4. Migration Strategy
1. **Phase 1: Database Foundation**: Create the `operational_zones` table and RLS policies.
2. **Phase 2: Domain Refactoring**: Introduce `ShiftPattern`, `SLAPenalties`, and `OperationalZone` to Dart domain.
3. **Phase 3: Engine Upgrade**: Modify the Evaluation Engine to project `ContractualServiceExecution` records daily based on the active `ShiftPattern`s. 
4. **Phase 4: UI Overhaul**: Replace `DeclareContractPlanForm` with the new B2B-focused wizard.

## 5. Risk Assessment (Council Validation)
- **Architect**: Zero infrastructure leakage. Geofencing is pushed back to the infrastructure layer mapping `zoneId` to coordinates.
- **UX/Ops**: Massive reduction in cognitive load. Operators configure business rules, not geospatial data.
- **Senior Engineer**: Riverpod providers must be properly scoped to fetch `OperationalZones` efficiently. The daily cron projection must be idempotent.
- **QA/Security**: The conversion from `ShiftPattern` + Local Time to absolute UTC `contractual_service_executions` must be perfectly deterministic, accounting for Daylight Saving Time (DST) anomalies in the specified timezone. Idempotency must prevent duplicate SET generation for the same operational day.
